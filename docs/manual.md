## 1. Sentinel이 하는 일

```
점검 등록  →  스케줄 실행  →  결과가 바뀌면 알림
(케이스)      (cron)          (실패·복구·응답시간 악화)
```

- API에 보낼 요청과 정상 응답의 조건을 케이스로 등록
- 정해진 시각마다 자동 실행
- 통과하던 점검이 실패하거나, 실패하던 점검이 복구되면 Slack·Teams로 알림

나머지 기능은 이 흐름을 받쳐 주는 역할

| 묶음 | 기능 | 하는 일 |
|------|------|---------|
| 판정을 정확하게 (8장) | 값 추출, 환경 변수·시크릿, 문서 가져오기 | 로그인 → 조회 같은 여러 단계 점검, 같은 케이스를 여러 환경에서 |
| 헛알림 줄이기 (9장) | 자동 재시도, 계속 실패 시 1시간 간격 재알림, 점검 시간, 휴일 | 잠깐의 흔들림·예정된 중단이 알림으로 오지 않게 |
| 알림이 없을 때도 믿을 수 있게 (10장) | 모니터링 공백, 알림 이력, 외부 생존 신호 | "알림이 없었다"가 정말 정상이었는지 확인 |
| 원인 파악 (11장) | 결과 화면, 직전 실행 대비 변화, 대시보드 | 알림이 왔을 때 GW·네트워크 문제인지 API 문제인지 먼저 가름 |
| 배포 때 같은 점검 쓰기 (12장) | API 토큰, CI 연동 | 배포 직후 같은 스위트로 확인 |

### 구성

```
프로젝트 (예: 결제)
 ├─ 환경 (dev, staging …)     기본 URL, 변수, 시크릿
 └─ 스위트 (예: 결제 기본 점검)
     ├─ 케이스 1, 2, 3 …      요청 1건 + 판정 규칙 + 값 추출
     └─ 스케줄                 어느 환경에서 언제 실행할지 (cron)
```

| 용어 | 의미 |
|------|------|
| 프로젝트 | 점검 대상 서비스 단위. 환경·스위트·알림 채널을 가짐 |
| 환경 | 같은 API의 배포 위치 (dev, staging 등). 기본 URL과 변수·시크릿을 가짐 |
| 스위트 | 함께 실행하는 케이스 묶음. 정해진 순서대로 실행 |
| 케이스 | HTTP 요청 1건과 그 응답의 판정 규칙 |
| 판정 규칙 | 응답이 정상인지 보는 조건 (상태 코드, 응답 시간, 헤더, JsonPath, 본문 포함) |
| 실행 | 스위트(또는 일부 케이스)를 한 환경에서 한 번 돌린 기록 |
| 스케줄 | 스위트를 정해진 시각마다 한 환경에서 실행하는 설정 |

- 같은 스위트를 환경만 바꿔 실행 가능 (dev에서 확인한 케이스를 staging에서 그대로)
- 실패 알림·대시보드 통계는 스케줄 실행 기준. 수동 실행은 수정 확인용이 많아 제외

### 역할

| 역할 | 할 수 있는 일 |
|------|---------------|
| 구성원 | 프로젝트·환경·스위트·케이스·스케줄 등록·수정·삭제, 실행, 모든 이력 조회, 프로젝트 알림 채널 지정, 본인 API 토큰 |
| 관리자 | 구성원 기능 + 사용자 초대·삭제, 비밀번호 재설정 링크 발급, 휴일 등록·삭제, 시스템 상태, 기본 알림 채널 테스트 |

### 화면 공통

- 시각은 모두 한국 시간(KST) `YYYY-MM-DD HH:mm:ss`
- 사이드바 메뉴: 홈, 프로젝트, 케이스 검색, 실행 이력, 스케줄, 변경 이력, 알림 이력, 휴일 (관리자는 사용자, 시스템 상태 추가)
- 사이드바 아래 계정 영역: 테마(시스템 설정·라이트·다크, 고르기 전에는 다크), 비밀번호 변경, API 토큰, API 문서, 로그아웃
- 좁은 화면(768px 미만)은 메뉴 버튼으로 사이드바 서랍 열기
- 항목별 수정·삭제·복제 등은 행 오른쪽 "⋯" 메뉴
- 삭제는 보관 처리. 확인 창에 함께 보관되는 하위 항목 표시, 지난 실행 이력은 그대로 유지. 같은 이름으로 다시 등록 가능

## 2. 설치

관리자가 서버에 한 번 설치. 세부 확인 항목·업데이트·되돌리기·인증서 교체·암호화 키 교체·백업은 [deploy.md](deploy.md)

### 2.1 준비

| 항목 | 내용 |
|------|------|
| 서버 | 상시 켜진 서버 (리눅스 권장). Docker Engine과 Compose v2, git, openssl |
| DB | PostgreSQL. 운영은 AWS RDS의 `sentinel` 스키마, 암호화 연결(`sslmode=require`). 타임아웃 조건은 [deploy.md](deploy.md) "서버 준비" |
| 접속 주소 | 내부 DNS 이름 (예: `sentinel.<내부 도메인>`)을 서버 IP로 등록 |
| 인증서 | 보유 인증서, 내부 인증 기관, Let's Encrypt 중 하나. 고르는 순서는 2.3 |
| 네트워크 | 사용자 PC → 서버 443 (HTTP를 HTTPS로 넘기려면 80도), 서버 → DB 5432, 서버 → 점검 대상 API, 서버 → Slack·Teams Webhook |
| 시계 | 시계 동기화(NTP). 인증서 유효기간·스케줄 시각의 기준 |

- 재부팅 후 자동 복구: `systemctl enable docker`. 컨테이너는 Docker와 함께 다시 시작
- web(3000)·api(8080)는 서버 안(`127.0.0.1`)에만 열려 있어 따로 막을 필요 없음

### 2.3 설정

인증서 방식 고르기

무료·PC 작업 없음·간단한 설정을 모두 만족하는 방식은 없어 하나는 포기. 아래 순서로 고름

```
조직 인증서(기관 발급)를 받을 수 있나?
 ├─ 예 → 보유 인증서
 └─ 아니요 → 접속할 사람이 몇 명인가?
      ├─ 적음 → 내부 인증 기관 + PC마다 루트 인증서 등록
      └─ 많음 → 공개 도메인으로 Let's Encrypt (DNS 인증)
```

| 방식 | PC 작업 | 비용 | 서버 쪽 할 일 | 포기하는 것 |
|------|---------|------|---------------|-------------|
| 보유 인증서 | 없음 (PC가 이미 신뢰) | 기관 정책 | 인증서 파일 배치, 만료 전 교체 ([deploy.md](deploy.md) "인증서 교체") | 발급 절차·교체 수작업 |
| 내부 인증 기관 | 접속하는 PC마다 1회 등록 (2.5) | 무료 | 없음. Caddy가 발급·갱신 | PC 작업 (사용자가 늘면 부담) |
| Let's Encrypt (DNS 인증) | 없음 | 무료 (도메인 비용 별도) | 처음 설정 (아래) | 초기 설정, DNS 권한 관리 |

- 내부 인증 기관도 PC를 중앙에서 관리(Windows 그룹 정책, MDM 등)하면 루트 인증서를 일괄 배포해 사용자 작업 없앨 수 있음
- 방식은 나중에 바꿀 수 있음: `.env`의 `SENTINEL_TLS`(와 보유 인증서면 `proxy/certs/`) 수정 후 `docker compose up -d sentinel-proxy`. 케이스·실행 이력·사용자 데이터는 그대로
  - 내부 인증 기관으로 시작해 조직 인증서를 받으면 바꾸는 순서도 가능
  - 내부 인증 기관을 그만 쓰면 PC에 등록한 루트 인증서 삭제 (2.5 "주의")

Let's Encrypt (DNS 인증)의 부담

내부망 서버는 인터넷에서 닿지 않아 일반 확인(80번 포트 접속) 대신 도메인 DNS에 TXT 값을 넣어 주인임을 증명. 그래서

- DNS를 직접 고칠 수 있는 공개 도메인 필요 (없으면 구입)
- 90일마다 자동 갱신하려면 서버가 DNS에 직접 쓰는 API 토큰 보관. 새면 도메인 레코드를 바꿀 수 있어 피해 범위가 큼. 권한을 그 도메인의 DNS 수정으로만 좁힐 수 있는 DNS 업체 선택
- 지금 Caddy 이미지에는 DNS 업체 모듈이 없음. 모듈을 넣은 이미지를 직접 빌드하거나, 다른 곳(certbot 등)에서 받은 인증서를 보유 인증서 방식으로 넣고 만료 전 교체
- 사용자 PC용 내부 DNS(이름 → 내부 IP)와 발급 확인용 공개 DNS(TXT)를 따로 관리
- 발급한 인증서 이름이 공개 기록(CT 로그)에 남아 내부 서버 이름이 알려짐 (IP·내용은 아님)
- 갱신이 실패하면(DNS 업체 장애, 토큰 만료) 만료일에 접속 불가

공개 도메인이고 80·443이 인터넷에서 열려 있는 서버라면 DNS 인증 없이 자동 발급 (`SENTINEL_TLS`에 관리자 이메일, [README.md](../README.md) 참고)

1. 인증서 배치 (보유 인증서만): `mkdir -p proxy/certs` 후 두 파일 복사 (git에는 올라가지 않음)
   - `proxy/certs/cert.pem`: 서버 인증서 뒤에 중간 인증서를 이어 붙인 파일 (서버 → 중간 순). 중간 인증서가 빠지면 일부 PC에서 신뢰 오류
   - `proxy/certs/key.pem`: 암호가 없는 개인 키. 복사 후 `chmod 600 proxy/certs/key.pem`
   - 내부 인증 기관은 이 단계 없음
2. `.env` 작성: `cp .env.example .env`

   | 값 | 보유 인증서 | 내부 인증 기관 |
   |----|-------------|----------------|
   | `SENTINEL_SITE_ADDRESS` | 접속 이름 (예: `sentinel.<내부 도메인>`). 인증서에 있는 이름만 | 접속 이름 (예: `sentinel.<내부 도메인>`) |
   | `SENTINEL_TLS` | `/certs/cert.pem /certs/key.pem` | `internal` (기본값) |
   | `SENTINEL_HSTS_MAX_AGE` | 처음에는 `300`(5분). 확인을 마치면 `31536000`(1년) | `0` 유지. 켜면 루트 인증서를 등록하지 않은 PC는 경고를 넘길 수 없어 접속 불가 |

3. `sentinel.env` 작성: `cp sentinel.env.example sentinel.env`, `chmod 600 sentinel.env`

   | 값 | 필수 | 설명 |
   |----|:----:|------|
   | `DB_URL` | O | `jdbc:postgresql://<RDS 엔드포인트>:5432/<DB>?currentSchema=sentinel&sslmode=require` |
   | `DB_USERNAME`·`DB_PASSWORD` | O | DB 계정 |
   | `SENTINEL_SECRET_KEY` | O | `openssl rand -base64 32`로 생성. 시크릿·프로젝트 Webhook 암호화용. 없으면 둘 다 등록 불가, 잃어버리면 저장된 값을 풀 수 없어 비밀번호 관리 도구에 따로 보관 |
   | `SENTINEL_ADMIN_EMAIL`·`SENTINEL_ADMIN_PASSWORD` | O | 최초 관리자. 사용자가 없을 때 1회 생성 |
   | `SENTINEL_WEB_URL` | | `https://<접속 이름>`. 알림의 결과·대시보드 링크 |
   | `SENTINEL_WEBHOOK_URL` | | 기본 알림 채널 (Slack·Teams Webhook). 없으면 알림이 서버 로그에만 남음 |
   | `SENTINEL_HEARTBEAT_URL` | | 외부 생존 신호 주소 (10.1) |

   - 예시 파일에서 `#`으로 막혀 있는 줄은 `#`을 지우고 값 입력
   - Webhook·생존 신호 주소와 비밀번호는 자격증명. 저장소·메신저에 올리지 않음
   - 값에 `$`·`\`·` #`가 있으면 작은따옴표로 감쌈 (`DB_PASSWORD='pa$word'`). 따옴표가 없거나 큰따옴표면 docker compose가 `$` 뒤를 변수로 바꿔 DB 접속 실패. `.env`도 같음

### 2.4 점검과 기동

```bash
scripts/preflight.sh
docker compose up -d --build --wait
```

- `scripts/preflight.sh`: 인증서 만료·키 짝·접속 이름 포함(보유 인증서), 설정 파일 권한·작성 형식·필수 값 확인. 마지막 줄 `Failures: 0` 확인 (값은 출력하지 않음)
- 내부 인증 기관이면 첫 기동 때 Caddy가 루트 인증서와 서버 인증서를 만듦
- 기동은 이미지 빌드 포함 몇 분. `--wait`는 모든 컨테이너가 정상이 될 때까지 대기

### 2.5 인증서 생성과 등록 (내부 인증 기관만)

보유 인증서는 이 단계 없음

구조

```
루트 인증서 (약 10년)        PC마다 1회 신뢰 등록
 └─ 중간 인증서 (약 7일)     Caddy가 자동 갱신
     └─ 서버 인증서 (약 12시간)  접속 이름마다, Caddy가 자동 갱신
```

- 사람이 할 일은 루트 인증서를 PC에 등록하는 것뿐. 중간·서버 인증서는 만료 전에 Caddy가 새로 발급

1. 생성 확인 (서버)

   첫 기동(2.4) 때 Caddy가 루트 인증서와 서버 인증서를 자동으로 만듦. 따로 발급 명령 없음

   ```bash
   docker compose exec sentinel-proxy ls /data/caddy/pki/authorities/local/
   docker compose exec sentinel-proxy ls /data/caddy/certificates/local/
   ```

   - 첫 줄: `root.crt`·`root.key`·`intermediate.crt`·`intermediate.key`가 있으면 인증 기관 생성 완료
   - 둘째 줄: 접속 이름(`SENTINEL_SITE_ADDRESS`)마다 폴더가 있으면 서버 인증서 발급 완료
   - 접속 이름을 바꾸거나 추가하면 `.env` 수정 후 `docker compose up -d sentinel-proxy`. 새 이름의 서버 인증서만 새로 발급되고 루트 인증서는 그대로 (PC 재등록 불필요)

2. 루트 인증서 꺼내기 (서버)

   ```bash
   docker compose cp sentinel-proxy:/data/caddy/pki/authorities/local/root.crt ./sentinel-root.crt
   openssl x509 -in sentinel-root.crt -noout -subject -enddate -fingerprint -sha256
   ```

   - 이름 `Caddy Local Authority - <연도> ECC Root`, 만료는 약 10년 뒤
   - `sentinel-root.crt`는 `.gitignore`에 있어 커밋되지 않음
   - 파일과 SHA-256 지문(`SHA256 Fingerprint=` 뒤 값)을 함께 전달. 지문은 파일과 다른 경로로 (예: 파일은 공유 폴더, 지문은 메신저)

3. PC에 등록 (접속하는 PC마다)

   먼저 받은 파일의 지문을 확인해 전달받은 값과 같은지 비교 (변조 확인). Windows는 Git Bash 등에 들어 있는 openssl로 같은 명령

   ```bash
   openssl x509 -in sentinel-root.crt -noout -fingerprint -sha256
   ```

   | PC | 등록 |
   |----|------|
   | macOS | `sentinel-root.crt` 더블클릭 → 키체인 "시스템" 선택 후 추가 (Mac 비밀번호) → 키체인 접근 → 시스템 → 인증서에서 `Caddy Local Authority …` 열기 → "신뢰" → "이 인증서 사용 시"를 "항상 신뢰" → 창 닫기 (비밀번호) |
   | Windows | `sentinel-root.crt` 더블클릭 → "인증서 설치" → 저장소 위치 "로컬 컴퓨터" → "모든 인증서를 다음 저장소에 저장" → "신뢰할 수 있는 루트 인증 기관" → 마침 |
   | Ubuntu·Debian | `sudo cp sentinel-root.crt /usr/local/share/ca-certificates/` 후 `sudo update-ca-certificates` |

   - macOS 터미널로는 `sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain sentinel-root.crt` (화면 등록과 같음)
   - Chrome·Edge·Safari는 운영체제에 등록한 인증서를 사용. 등록 전부터 열려 있던 브라우저는 다시 시작
   - Firefox에서 경고가 계속되면 Firefox 설정의 인증서 관리에서 따로 가져오기
   - CI 러너는 등록 대신 `SENTINEL_CA_CERT`에 이 파일 경로 (12.2)

4. 등록 확인 (PC)

   ```bash
   curl -sS -o /dev/null -w '%{http_code}\n' https://<접속 이름>/login
   ```

   - `200`이면 신뢰 완료. 등록 전에는 `SSL certificate problem: unable to get local issuer certificate`
   - 브라우저에서 `https://<접속 이름>`을 열어 경고 없음 확인
   - macOS의 `security verify-cert`가 "signed certificate timestamps (SCTs)" 부족을 출력해도 무관 (공개 인증서에만 적용하는 검사)

주의

- 등록 전에는 브라우저에 인증서 경고. 넘기면 접속은 되나 매번 확인 필요
- `sentinel-root.crt`는 공개 인증서라 나눠 줘도 됨. 루트 인증서의 개인 키(`root.key`)는 서버의 `caddy_data` 볼륨에만 두고 꺼내지 않음
- `docker compose down -v`로 볼륨을 지우면 새 루트 인증서가 만들어져 모든 PC에 다시 등록해야 함. `-v` 없이 사용하고 볼륨은 백업
- 더 이상 쓰지 않으면 PC에서 등록한 인증서 삭제 (macOS 키체인 접근, Windows 인증서 관리 `certlm.msc`)

### 2.6 확인

다른 PC 브라우저에서

1. `https://<접속 이름>` 접속 시 인증서 경고 없음 (내부 인증 기관은 루트 인증서를 등록한 PC에서), `http://`는 `https://`로 이동
2. 최초 관리자로 로그인
3. 사이드바 "시스템 상태": 버전 1.2.0, 암호화 키 "사용 중", 알림·감시 설정이 "설정됨" (없는 항목은 `sentinel.env` 확인)
4. "알림 이력" → "기본 채널 테스트 알림"으로 기본 채널에 메시지가 오는지 확인
5. 생존 신호를 설정했다면 외부 감시 서비스에 첫 신호 도착 (1분 안)

### 2.7 마무리

1. 최초 관리자 비밀번호 변경: 계정 영역 → "비밀번호 변경"
2. `sentinel.env`에서 `SENTINEL_ADMIN_PASSWORD` 줄 삭제 후 컨테이너 다시 만들기

   ```bash
   docker compose up -d sentinel-api
   ```

   - 줄만 지우면 실행 중인 컨테이너의 환경변수에는 남아 있으므로 다시 만들어 제거
3. 보유 인증서면 확인을 마친 뒤 `.env`의 `SENTINEL_HSTS_MAX_AGE`를 `31536000`으로 바꾸고 `docker compose up -d sentinel-proxy` (내부 인증 기관은 `0` 유지)

### 2.8 운영 시작 설정

화면에서 관리자가 1회

1. 사용자 초대: 사이드바 "사용자" → "사용자 초대" (14.1)
2. 휴일 등록: 사이드바 "휴일" → "여러 건 붙여넣기"로 올해 남은 공휴일과 내년 공휴일 (9.4)
3. 프로젝트별 알림 채널이 필요하면 프로젝트 화면 "알림 채널" (7.2)
4. 이후 점검 등록은 4장 "처음 시작하기"

- DB 구조가 바뀌는 릴리스는 먼저 DB 스냅샷. 확인 방법·되돌리기는 [deploy.md](deploy.md) "업데이트"·"되돌리기"

## 3. 로그인과 계정

### 가입

가입은 관리자가 보낸 초대 링크로만 가능 (공개 가입·메일 발송 없음)

1. 관리자에게 받은 초대 링크 열기 (`/invites/...`)
2. 이름·비밀번호(10자 이상) 입력
3. 바로 로그인된 상태로 시작

- 초대 링크 유효 기간 7일, 한 번만 사용 가능
- "초대 링크가 만료되었거나 이미 사용·취소되었습니다" 안내가 나오면 관리자에게 새 링크 요청

### 로그인·로그아웃

- 로그인 세션 유효 기간 12시간. 지나면 로그인 화면으로 이동하고, 로그인 후 원래 보던 화면으로 복귀
- 로그인 실패 사유(이메일 없음·비밀번호 틀림)는 구분해서 알려 주지 않음
- 로그아웃: 사이드바 계정 영역의 "로그아웃"

### 비밀번호

| 상황 | 방법 |
|------|------|
| 비밀번호 변경 | 계정 영역 → "비밀번호 변경" (`/settings/password`). 현재·새 비밀번호 입력. 변경하면 모든 기기에서 로그아웃 |
| 비밀번호 분실 | 관리자에게 재설정 링크 요청 → 링크에서 새 비밀번호 설정 → 로그인 화면에서 다시 로그인 |

- 재설정 링크 유효 기간 2시간, 한 번만 사용 가능
- 재설정 링크로 바꾸면 본인의 API 토큰도 모두 폐기 (계정 복구로 보고 CI 연동도 끊음). 본인이 직접 변경할 때는 API 토큰 유지

## 4. 처음 시작하기

dev 환경의 API 1개를 평일 오전마다 점검하고 실패하면 알림 받는 예

스케줄이 하나도 없는 동안 홈 맨 위에 "처음 시작하기"가 같은 순서로 남은 단계와 그 단계를 할 화면("이동")을 표시. 첫 스케줄을 추가하면 사라짐

1. 프로젝트 등록: "프로젝트" → 새 프로젝트 (이름 예: `결제`). 등록하면 프로젝트 화면으로 이동
2. 환경 추가: 프로젝트 화면 "환경 추가" → 이름 `dev`, 기본 URL `https://dev-api.example.com`
   - 토큰이 필요하면 시크릿에 `token` 등록 (8.1 참고)
3. 스위트 추가: 프로젝트 화면 "스위트 추가" → 이름 `결제 기본 점검`
4. 케이스 추가: 스위트 화면 "케이스 추가"
   - 메서드 `GET`, 경로 `/billing/v1/health`
   - 판정 규칙: 상태 코드 `2xx`, 응답 시간 `2000`ms 이하
   - "등록 후 실행"으로 바로 확인
5. 결과 확인: 결과 화면에서 통과·실패와 응답 내용 확인. 실패면 케이스 수정 → "저장 후 실행" 반복
6. 알림 채널 확인: 프로젝트 화면 맨 아래 "알림 채널"에서 Slack·Teams Webhook 지정 후 "테스트 알림 보내기" (지정하지 않으면 서버 기본 채널). 스케줄을 켜기 전에 확인해야 첫 실패 알림을 놓치지 않음
7. 스케줄 추가: 스위트 화면 "스케줄" 영역 → 환경 `dev`, cron `10 9 * * 1-5` (평일 09:10), 필요하면 "휴일 건너뛰기" 체크

이후는 자동: 평일 09:10마다 실행, 실패하면 알림, 복구되면 복구 알림

케이스가 많으면 4번 대신 OpenAPI·Postman 문서에서 가져오기 (8.3 참고)

### 데모로 체험하기 (실제 API 없이)

점검할 API가 아직 없을 때, 함께 들어 있는 데모 API로 점검 등록 → 스케줄 → 실패·복구 알림까지 해 보는 방법. 설치한 서버(또는 로컬)에서 실행

데모 API (`demo/`, WireMock)

| 요청 | 응답 |
|------|------|
| `GET /health` | 200 `{"status": "UP"}` |
| `POST /auth/login` (`{"username": "demo", "password": "demo-password"}`) | 200 `{"token": ...}`, 그 외 401 |
| `GET /orders` (`Authorization: Bearer` 토큰) | 200 주문 목록. 장애 스위치를 켜면 503, 토큰 없으면 401 |
| `GET /orders/101` | 200 주문 1건, 다른 번호는 404 |
| `GET /reports/daily` | 200, 0.2~2.5초 사이로 응답 시간이 들쭉날쭉 |

1. 데모 API 기동

   ```bash
   docker compose --profile demo up -d sentinel-demo-api
   ```

2. 프로젝트 `데모`, 환경 `demo` (기본 URL `http://sentinel-demo-api:8080`, 변수 `orderId` = `101`), 스위트 `데모 쇼핑몰` 등록
3. 스위트 화면 "문서 가져오기" → "OpenAPI 3 (JSON·YAML)" → 저장소의 `demo/openapi.yaml` 내용 → 5건 모두 가져오기
   - 인증 안내 "add {{token}} as a secret of the environment, or if a login request issues it, extract it into {{token}} in an earlier case": 데모는 뒤쪽 방법(로그인 응답에서 값 추출, 다음 단계)
4. `Login` 케이스 수정 → 값 추출: 변수 이름 `token`, 위치 본문 JSON 값 `$.token`, 값 가리기 → 저장
   - 뒤 케이스들의 `Authorization: Bearer {{token}}`이 이 값으로 채워짐. 결과에는 `****`로 가려 저장
5. `Daily report` 케이스에 응답 시간 판정 `2000`ms 추가 → 가끔 실패해 "불안정" 배지·실패 원인을 볼 수 있음
6. 스위트 화면 오른쪽 위 "지금 실행" → 결과 화면에서 모두 통과 확인 (응답 시간이 길면 `Daily report`만 실패할 수 있음)
7. 스케줄 추가: 환경 `demo`, cron `* * * * *` (1분마다)
8. 장애 켜기 → 1~2분 안에 `List orders`가 503으로 실패, "알림 이력"에 `새로 실패` 알림

   ```bash
   curl -X POST http://127.0.0.1:18089/demo/outage/start
   ```

9. 장애 끄기 → 다음 실행에서 복구 알림

   ```bash
   curl -X POST http://127.0.0.1:18089/demo/outage/stop
   ```

10. 정리: 스케줄 끄기 또는 삭제, 데모 프로젝트 삭제, 데모 API 중지

    ```bash
    docker compose --profile demo stop sentinel-demo-api
    ```

- 알림 채널(Webhook)을 지정해 두면 같은 알림이 Slack·Teams로도 감
- 장애 스위치는 같은 PC(`127.0.0.1:18089`)에서만 열림. 데모 API를 다시 시작하면 장애가 꺼진 상태로 돌아감
- 데모 API는 `--profile demo`를 줄 때만 뜸. 평소 `docker compose up`에는 포함되지 않음

## 5. 점검 만들기

### 5.1 프로젝트

- "프로젝트" 화면에서 목록 확인·새 프로젝트 등록
- 프로젝트 화면(`/projects/{id}`): 이름·설명 수정, 삭제, 환경·스위트 관리, 점검 시간, 알림 채널
- 프로젝트를 삭제하면 그 안의 환경·스위트·케이스·스케줄도 함께 보관

### 5.2 환경

| 항목 | 설명 |
|------|------|
| 이름 | `dev`, `staging` 등 |
| 기본 URL | 케이스 경로 앞에 붙는 주소. 예: `https://dev-api.example.com` |
| 변수 | 케이스의 경로·헤더·본문에서 `{{이름}}`으로 치환할 일반 값 |
| 시크릿 | 토큰·API 키처럼 감출 값. 같은 `{{이름}}`으로 사용 (8.1) |

- 환경 이름 옆 `#번호`는 환경 ID (CI 연동에서 사용)
- 환경 복제: 환경 "⋯" → "환경 복제". 기본 URL·변수를 채운 등록 창이 열림. 시크릿은 이름만 채워지므로 값을 다시 입력

### 5.3 스위트 화면

스위트 화면(`/suites/{id}`)에서 할 수 있는 일

- 스위트 이름·설명 수정, 삭제
- 화면 오른쪽 위에서 환경을 골라 "지금 실행" (환경이 하나면 미리 선택됨, 끝나면 결과 화면으로 이동)
- 스케줄 등록·수정·켜기·끄기·삭제 (6장)
- 케이스 목록(실행 순서대로): "케이스 추가", "순서 변경", "문서 가져오기"
- 케이스 "⋯" 메뉴: 실행, 여기까지 실행(첫 케이스 제외), 수정, 복제, 변경 이력, 삭제
- 화면 아래 응답시간: 케이스별 건수·p50·p95·최대와 일별 추세 차트
- 케이스 이름 옆 배지

  | 배지 | 의미 |
  |------|------|
  | 불안정 | 최근 7일 스케줄 실행에서 실패·통과를 반복하거나 응답이 없어 다시 보낸 일이 잦음. 배지에 마우스를 올리면 환경별 이유 |
  | 느림 | 응답시간 악화 알림 후 아직 회복하지 않음. 환경별 감지 당시 p95 변화 |

### 5.4 케이스 등록·수정

"케이스 추가"(`/cases/new`) 또는 케이스 "⋯" → "수정"(`/cases/{id}`)

| 영역 | 내용 |
|------|------|
| 요청 | 메서드, 경로, 헤더, 본문 |
| 판정 규칙 | 응답이 정상인지 보는 조건. 여러 개면 모두 통과해야 통과 |
| 값 추출 | 응답에서 값을 꺼내 뒤 케이스에서 사용 (8.2) |

- 경로는 `/` 또는 `{{변수}}`로 시작. 기본 URL 뒤에 붙음 (예: `/orders/{{orderId}}`)
- 경로·헤더·본문의 `{{이름}}`은 실행할 때 환경 변수·시크릿·추출 값으로 치환
- 입력 오류는 저장 전에 항목별로 한 번에 표시 (예: `판정 규칙 2 (본문 포함): 포함할 문자열을 입력해 주세요`)
- 저장 버튼

  | 버튼 | 동작 |
  |------|------|
  | 등록 / 저장 | 저장 후 스위트 화면으로 |
  | 등록 후 실행 / 저장 후 실행 | 저장하고 이 케이스만 실행, 결과 화면으로 |
  | 저장 후 여기까지 실행 | 저장하고 스위트 처음부터 이 케이스까지 실행 (첫 케이스 제외). 앞 케이스의 추출 값이 필요한 케이스 확인용 |

- 다른 사람이 같은 케이스를 먼저 저장했으면 저장하지 않고 "modified by another request; reload and try again" 안내 → 새로고침 후 다시 수정 (환경 수정도 같음)

### 5.5 판정 규칙

| 규칙 | 입력 | 예 |
|------|------|-----|
| 상태 코드 | 허용할 코드 목록. `x`는 아무 숫자 | `200`, `2xx`, `40x` |
| 응답 시간 | 상한(ms, 이하면 통과) | `2000` |
| 헤더 | 헤더 이름, 연산자, 값 | `Content-Type` 포함 `json` |
| JsonPath | 경로, 연산자, 기대값 | `$.items.length()` 초과 `0` |
| 본문 포함 | 포함할 문자열 (대소문자 구분) | `OK` |

연산자 (헤더·JsonPath)

| 연산자 | 헤더 | JsonPath | 의미 |
|--------|:----:|:--------:|------|
| 존재 / 없음 | O | O | 존재 여부 |
| 같음 (==) / 다름 (!=) | O | O | 일치 여부 |
| 포함 | O | O | 부분 문자열 또는 배열 원소 포함 |
| 정규식 일치 | O | O | 정규식 부분 일치 (문자열만) |
| 초과 (>) / 이상 (>=) / 미만 (<) / 이하 (<=) | X | O | 숫자 비교. 숫자가 아니면 실패 |

JsonPath 기대값 입력

- JSON으로 해석: `1000`·`true`는 숫자·불리언, 문자열 숫자는 `"1000"`처럼 따옴표
- 숫자 비교는 값 기준 (`1`과 `1.0` 같음), 문자열 `"1000"`과 숫자 `1000`은 다름
- 그 외 입력은 문자열로 취급
- HTML 오류 페이지처럼 본문이 JSON이 아니면 JsonPath 규칙 실패 (`response body is not JSON`)

규칙은 하나가 실패해도 전부 평가해 결과 화면에 규칙별로 표시

### 5.6 수동 실행

케이스를 만들고 고칠 때 바로 확인하는 용도. 알림·대시보드 통계에는 들어가지 않음

| 방법 | 위치 | 실행 범위 |
|------|------|-----------|
| 스위트 실행 | 스위트 화면 오른쪽 위에서 환경 선택 → "지금 실행" | 스위트의 모든 케이스 |
| 케이스 실행 | 케이스 "⋯" → "실행", 케이스 화면 "저장 후 실행" | 그 케이스만 |
| 여기까지 실행 | 케이스 "⋯" → "여기까지 실행", "저장 후 여기까지 실행" | 스위트 처음부터 그 케이스까지 |
| 실패만 다시 실행 | 결과 화면 "실패만 다시 실행" | 실패·오류 케이스 + 그 케이스가 쓰는 추출 값을 만드는 앞 케이스 |

- 진행 중인 실행은 결과 화면에서 "중지" (확인 창). 진행 중이던 케이스까지 기록
- 점검 시간·휴일에도 수동 실행은 가능
- 결과 읽는 법은 11.1

### 6.1 등록·수정

스위트 화면 "스케줄" 영역에서 등록, cron·환경 수정, 켜기·끄기, 삭제

| 항목 | 설명 |
|------|------|
| 실행 환경 | 같은 프로젝트의 환경. 나중에 바꿔도 지난 실행 이력은 유지 |
| cron | 5자리 `분 시 일 월 요일`, 한국 시간 기준 |
| 휴일 건너뛰기 | 켜면 등록한 휴일에 실행하지 않음. 목록에 "휴일 제외" 배지 (9.4) |

cron 예

| cron | 의미 |
|------|------|
| `10 9 * * 1-5` | 평일 09:10 |
| `*/10 * * * *` | 10분마다 |
| `0 * * * *` | 매시 정각 |
| `30 8-18 * * 1-5` | 평일 08:30~18:30 매시 30분 |
| `0 3 * * *` | 매일 03:00 |

- 같은 스위트에 환경별 스케줄 여러 개 가능 (dev는 10분마다, staging은 평일 오전 등)
- 밤에 꺼지는 환경은 업무 시간 cron(예: `30 8-18 * * 1-5`)으로. 상시 cron이면 꺼져 있는 동안 실패 알림이 이어짐. 정해진 날의 중단은 점검 시간, 쉬는 날은 휴일 건너뛰기 (9장)
- 켜면 지금 시각 기준으로 다음 실행 시각을 다시 계산, 끄면 다음 실행 시각 없음
- 서버는 60초마다 실행할 스케줄 확인. 몇십 초 늦게 시작할 수 있음
- 노트북 절전 등으로 놓친 실행은 켜진 뒤 1회만 실행하고 다음 시각으로

### 6.2 전체 스케줄

사이드바 "스케줄"(`/schedules`)

## 7. 알림 받기

### 7.1 알림 종류

스케줄 실행 결과를 같은 스위트·환경의 이전 스케줄 실행과 비교해 발송. 수동 실행은 알림 없음

| 알림 | 발송 시점 |
|------|-----------|
| `{환경} {스위트} - N건 중 M건 실패 (새로 실패 K건)` | 실패·오류가 있을 때. 새로 실패한 케이스가 있으면 바로 |
| `… (계속 실패 중)` | 이미 실패하던 케이스만 계속 실패할 때. 1시간마다 한 번 (9.2) |
| `{환경} {스위트} - 복구, N건 모두 통과` | 실패 뒤 모두 통과했을 때 1회 |
| `{프로젝트} - 응답시간 악화 N건` / `- 응답시간 회복 N건` | 매시 5분 확인. 최근 24시간 p95가 그 전 7일보다 50% 이상 그리고 100ms 이상 느릴 때 1회, 돌아오면 1회 |
| `주간 요약 MM-dd ~ MM-dd` | 매주 월요일 09:00, 지난주 실행 수·통과율·실패 원인·불안정 케이스·느려진 케이스·모니터링 공백 |
| `모니터링 공백 - 스케줄이 제때 실행되지 않음` | Sentinel이 멈췄다 다시 켜졌을 때 (10.1) |
| `DB 연결 실패 - 스케줄 실행 중단` / `DB 연결 복구 - 스케줄 실행 재개` | DB 접속 실패·복구 시 1회씩 |
| `스케줄 {id} 실행 오류` | 스케줄 실행 자체가 중단됨 (시크릿을 읽지 못하는 경우 등). 같은 사유는 1시간마다 |

실패 알림 예

```
[Sentinel] dev 결제 - 12건 중 2건 실패 (새로 실패 1건)
[새로 실패] 결제 승인 · POST /billing/v1/charge → status in [2xx]: was 500
[3회째 · 09-24 09:10부터] 결제 내역 · GET /billing/v1/history → response time <= 2000ms: was 3200ms
계속 실패하면 1시간마다 다시 알림 (새로 실패·복구는 바로)
결과: https://sentinel.example.com/runs/12
```

- 케이스마다 `[새로 실패]` 또는 `[N회째 · 시작 시각부터]`
- 응답이 없어 다시 보낸 뒤에도 실패하면 사유 끝에 "(N회 다시 보낸 뒤)"
- 일부만 복구되면 복구 알림 없이 다음 재알림에 남은 실패만 표시
- 결과·대시보드 링크는 서버에 화면 주소가 설정된 경우

### 7.2 알림 채널

| 채널 | 받는 알림 | 지정 |
|------|-----------|------|
| 기본 채널 | 프로젝트 채널이 없는 프로젝트의 알림, DB 연결·모니터링 공백·스케줄 실행 오류, 주간 요약 | 서버 설정 (관리자) |
| 프로젝트 채널 | 그 프로젝트의 실패·복구, 응답시간 악화·회복 | 프로젝트 화면 맨 아래 "알림 채널" (모든 사용자) |

프로젝트 채널 지정

1. 프로젝트 화면 "알림 채널" → Webhook 주소 입력 후 저장
2. "테스트 알림 보내기" → 결과(받음·상태 코드·못 보낸 사유) 확인
3. 기본 채널로 돌아가려면 "기본 채널로 되돌리기"

- Webhook 주소는 자격증명이라 암호화 저장, 저장 후 다시 표시하지 않음. 바꾸려면 새 주소 입력
- 메시지 형식은 주소로 자동 판별: Slack(`hooks.slack.com`), Teams 워크플로·커넥터, 그 외는 `{"text": "..."}` 한 필드
- 알림 성격별 색: 실패·장애(빨강), 악화·공백(주황), 복구·회복(초록), 요약·확인(회색)

## 8. 판정을 정확하게

### 8.1 환경 변수와 시크릿

같은 케이스를 환경마다 다른 값으로 실행하는 방법

| 구분 | 저장 | 화면 표시 | 용도 |
|------|------|-----------|------|
| 변수 | 평문 | 값까지 | `userId`, `apiPrefix` 같은 일반 값 |
| 시크릿 | 암호화 | 이름만 | 토큰·API 키 |

- 둘 다 `{{이름}}`으로 사용. 변수와 시크릿에 같은 이름은 사용 불가
- 시크릿
  - 저장한 값은 다시 볼 수 없음
  - 값 변경: 같은 이름으로 다시 입력 후 저장
  - 삭제: 이름 옆 삭제 후 저장. 저장 전까지 취소 가능
  - 실행 이력(요청·응답·판정 메시지)에는 `****`로 가려서 저장. 실제 요청에는 원래 값으로 전송
  - "시크릿 기능이 꺼져 있습니다" 안내가 나오면 서버에 암호화 키가 없는 상태 → 관리자에게 문의

### 8.2 값 추출

앞 케이스 응답의 값을 같은 스위트 실행의 뒤 케이스가 `{{변수}}`로 사용. 로그인 → 조회, 등록 → 조회·삭제 같은 여러 단계 점검용

| 항목 | 설명 |
|------|------|
| 변수 이름 | 영문·숫자·`_ . -`, 100자 이하 |
| 위치 | 본문 JSON 값(JsonPath) 또는 응답 헤더(헤더 이름) |
| 값 가리기 | 토큰처럼 감출 값. 이후 기록되는 요청·응답·판정 메시지에서 `****` |

예

| 케이스 | 값 추출 | 다음 케이스에서 |
|--------|---------|-----------------|
| 1. 로그인 `POST /auth/login` | `token` ← 본문 `$.data.token` (가리기) | 헤더 `Authorization: Bearer {{token}}` |
| 2. 주문 등록 `POST /orders` | `orderId` ← 본문 `$.id` | 경로 `/orders/{{orderId}}` |

- 케이스당 최대 20개. 문자열·숫자·불리언만 추출 가능
- 추출 실패(경로·헤더 없음, `null`, 객체·배열)는 그 케이스 실패로 기록
- 추출한 값은 환경 변수의 같은 이름보다 우선
- 추출에 실패하면 그 변수를 비우므로 뒤 케이스는 `UNRESOLVED_VARIABLE` 오류 (환경 변수 값으로 조용히 실행되지 않음)
- 같은 스위트 실행 안에서, 실행 순서상 뒤 케이스만 사용 가능
  - 케이스 1건만 실행하면 앞 케이스를 실행하지 않아 추출 값이 비어 있음 → "여기까지 실행" 사용
- 스위트 화면 케이스 목록의 요청 아래에 추출하는 변수 표시

### 8.3 문서에서 케이스 가져오기

스위트 화면 "문서 가져오기"

1. 형식 선택: OpenAPI 3 (JSON·YAML) 또는 Postman 컬렉션 v2 (JSON)
2. 문서 붙여 넣기 또는 파일 선택 → 미리보기
3. 후보 선택·이름 수정 → "N건 가져오기"

- 미리보기에 문서 제목·버전, 서버 주소(환경 기본 URL 설정 참고용), 변환 경고 표시
- 스위트에 이미 있는 이름의 후보는 선택 해제 상태로 시작. 빈 이름·중복 이름은 가져오기 버튼이 막힘
- 전부 등록되거나 전부 등록되지 않음 (일부만 등록되지 않음)
- 한도: 문서 5MB, 한 번에 500건
- 변환 요약
  - 경로 파라미터 `{petId}` → `{{petId}}`, 필수 query·header 파라미터도 변수로
  - 판정 규칙은 문서의 2xx 응답 코드, 없으면 `2xx`
  - JSON 요청 본문은 예시 값, 없으면 스키마로 만든 자리 표시 값 (경고 확인 후 수정)
  - 인증은 `Authorization: Bearer {{스킴 이름}}` 등 변수로. 어떤 변수를 시크릿으로 등록할지 경고에 안내. 로그인 API가 발급하는 토큰은 시크릿 대신 앞 케이스의 값 추출로 같은 이름의 변수에 받음 (8.2, 데모 4장)
  - Postman의 평문 자격증명은 변수로 바꾸고 값은 남기지 않음. 스크립트(pre-request·test)는 미지원
- 지원하지 않는 문서: Swagger 2.0, Postman v1 컬렉션·환경 파일
- 세부 변환 규칙은 [api/README.md](../api/README.md) "케이스 가져오기"

### 8.4 실행 순서·복제

- 순서 변경: 스위트 화면 "순서 변경" → 위·아래 버튼으로 한 칸씩 이동 후 저장. 목록·실행·값 추출 전달 모두 이 순서. 새 케이스는 마지막
- 창을 연 사이 다른 곳에서 케이스가 추가·삭제되면 저장하지 않고 안내. 다시 열면 최신 목록
- 복제: 케이스 "⋯" → "복제". 요청·판정 규칙·값 추출을 복사해 원본 바로 다음 순서로 등록하고 새 케이스 수정 화면으로 이동. 이름은 "원본 (복사)"

## 9. 헛알림 줄이기

### 9.1 응답이 없을 때 다시 보내기

GW·네트워크가 잠깐 흔들린 것만으로 실패가 기록·알림되지 않도록, 응답을 받지 못한 케이스는 1초 뒤 한 번 다시 보냄

| 오류 | 다시 보내기 |
|------|-------------|
| 연결 실패 | 모든 메서드 (요청이 서버에 닿지 않음) |
| 시간 초과·연결 끊김 | `GET`·`HEAD`·`OPTIONS`만 (등록·삭제 요청은 서버가 이미 처리했을 수 있어 두 번 보내지 않음) |
| TLS 오류, 막힌 목적지, 변수 누락·잘못된 요청 | 없음 (다시 보내도 같음) |

- 응답을 받은 뒤의 판정 실패는 다시 보내지 않음 (실제 문제일 가능성이 큼)
- 다시 보낸 케이스는 결과 화면에 "재시도 N회" 배지
- 재시도가 잦은 케이스는 "불안정"으로 표시 (11.3)

### 9.2 계속 실패 중 재알림

같은 케이스가 계속 실패하는 동안 스케줄 실행마다 같은 알림이 반복되지 않도록 1시간마다만 발송

| 이번 실행 | 발송 |
|-----------|------|
| 새로 실패한 케이스가 있음 | 바로 |
| 계속 실패 중인 케이스만, 1시간 안에 알림을 보냄 | 생략 |
| 계속 실패 중인 케이스만, 1시간이 지남 | 다시 알림 (`계속 실패 중`, 몇 회째·언제부터) |
| 모두 통과 (직전 실행에 실패) | 바로 복구 알림 |

### 9.3 점검 시간

배포·점검으로 실패가 예상되는 동안 그 환경의 스케줄 실행을 건너뜀. 실패 알림·통계에 점검 중 실패가 섞이지 않고, 끝나면 따로 조치 없이 다시 실행

1. 프로젝트 화면의 환경 "⋯" → "점검 시간 등록"
2. 시작·끝(KST, 기본 지금부터 1시간), 사유(선택, 예: `GW 배포`)

- 최대 7일 (켜 두고 잊어 감시가 멈추는 것 방지)
- 환경 이름 옆에 "점검 중 ~끝 시각" 또는 "점검 예정" 배지, 홈에 "점검 중인 환경"
- "점검 시간" 표의 "⋯": 수정(연장·단축·사유), 변경 이력, 진행 중이면 "지금 종료", 예정이면 "취소"
- 건너뛴 시각의 실행 기록은 남지 않음. 수동 실행은 점검 중에도 가능

### 9.4 휴일

공휴일·임시공휴일처럼 대상 시스템도 쉬는 날. 평일 cron(`1-5`)으로 거를 수 없는 날용

- 사이드바 "휴일"(`/holidays`): 연도별 목록, 오늘·다음 휴일, 이전·다음 해 이동
- 공휴일 자동 반영 없음. 대체공휴일·임시공휴일 포함 직접 등록
- 등록·삭제는 관리자만 (모든 스케줄에 영향), 조회는 모든 사용자
  - "휴일 추가": 날짜·이름
  - "여러 건 붙여넣기": 한 줄에 `날짜 이름`. 이미 등록한 날짜는 건너뜀

    ```
    2026-12-25 성탄절
    2027-01-01 신정
    ```
- 휴일 건너뛰기를 켠 스케줄만 해당 (24시간 감시 스케줄은 끄고 두면 휴일에도 실행)

## 10. 알림이 없을 때도 믿을 수 있게

### 10.1 모니터링 공백과 외부 생존 신호

- 모니터링 공백: Sentinel 중지·서버 절전·DB 연결 끊김 등으로 스케줄이 예정보다 10분 넘게 늦게 실행된 기간
  - 이 동안은 장애가 나도 실패 알림이 없으므로 "알림이 없었다 = 정상"이 아님
  - 다시 켜진 뒤에 알림이 가고 홈 대시보드에 남음 (건수·합계 길이, 최근 5건의 기간·제때 실행되지 않은 스케줄 수)
- 멈춘 그 순간 알려면 외부 생존 신호(healthchecks.io 등) 설정 필요. 서버 설정이라 관리자 몫 ([deploy.md](deploy.md))
- 설정 여부는 관리자의 "시스템 상태" → "알림·감시 설정"에서 확인

### 10.2 알림 이력

사이드바 "알림 이력"(`/notifications`). "알림이 안 왔다"를 서버 로그 없이 확인

- 보낸 알림 최신순 20건 단위 (90일 보관)
- 성격(실패·주의·복구·안내)·제목, 시각, 보낸 곳(프로젝트 또는 기본 채널 · Slack·Teams·텍스트·로그)
- 결과: 보냄, 로그에만 기록(기본 채널 주소 미설정), HTTP 상태, 응답 없는 사유
- 확인할 점 안내 (예: 404 → Webhook이 삭제되었거나 주소가 바뀜)
- 필터: 프로젝트 Webhook, 보내지 못한 것만
- 프로젝트 화면 "알림 채널"의 "발송 이력 보기"로 그 프로젝트 이력 바로 열기
- 관리자는 맨 위 "기본 알림 채널"에서 "기본 채널 테스트 알림"
- 최근 7일 마지막 발송이 실패한 채널은 홈 맨 위에도 표시

## 11. 원인 파악

### 11.1 결과 화면

실행 직후 이동하거나 알림의 결과 링크로 여는 화면(`/runs/{id}`)

- 진행 중: "실행 중 · N건 중 M건 완료", 끝난 케이스부터 자동으로 표시
- 케이스별 판정. 실패·오류 케이스는 펼친 상태로 표시
- 펼치면 판정 규칙별 결과, 값 추출 결과(가린 값은 "가림"), 요청·응답 헤더와 본문(JSON은 정렬)
- 실행 상태: 실행 중, 완료, 중지(누가 중지했는지 표시), 중단(서버 재시작 등으로 끝나지 못함)

판정

| 판정 | 의미 |
|------|------|
| 통과 | 판정 규칙 모두 통과 |
| 실패 | 응답은 받았지만 판정 규칙 실패. 4xx·5xx도 응답을 받은 것 |
| 오류 | 응답을 받지 못했거나 요청을 보내기 전에 실패. 사유 코드 표시 |

오류 사유

화면에는 이름과 확인할 점을 표시하고, 원래 코드와 서버 메시지를 함께 표시 (문의·검색용)

| 이름 | 코드 | 의미 | 확인할 것 |
|------|------|------|-----------|
| 변수 값 없음 | `UNRESOLVED_VARIABLE` | `{{변수}}` 값 없음, 요청 미전송 | 환경 변수·시크릿 이름, 앞 케이스의 값 추출 (단건 실행이면 "여기까지 실행") |
| 잘못된 요청 | `INVALID_REQUEST` | 잘못된 URL·헤더, 요청 미전송 | 경로, 변수 값의 공백 등 URL에 쓸 수 없는 문자 |
| 타임아웃 | `TIMEOUT` | 응답 대기 시간 초과 (기본 30초) | 대상 서버·GW 상태 |
| 연결 실패 | `CONNECTION_FAILED` | 연결 실패 (거부, 이름 해석 실패, 연결 시간 초과 5초) | 기본 URL, 서버 기동 여부, 방화벽 |
| 연결 끊김 | `IO_ERROR` | 주고받는 중 연결 끊김 | 대상 서버·GW 상태 |
| 인증서·TLS 오류 | `TLS_ERROR` | 인증서 만료·신뢰할 수 없는 발급자·이름 불일치, TLS 협상 실패 | 대상 서버의 인증서 |
| 막힌 목적지 | `BLOCKED_DESTINATION` | 링크 로컬·클라우드 메타데이터 주소라 전송하지 않음 | 기본 URL (사설망·루프백 주소는 허용) |
| Sentinel 내부 오류 | `UNEXPECTED` | Sentinel 내부 오류 | 관리자에게 문의 (서버 로그) |

- 요청·응답의 `Authorization`, `Cookie`, `Set-Cookie`, `X-Api-Key` 등 헤더 값과 시크릿은 `****`로 저장
- 응답 본문은 64KB까지 저장 (판정은 전체 본문 기준)
- 리다이렉트(3xx)는 따라가지 않고 그대로 기록

배지

| 배지 | 위치 | 의미 |
|------|------|------|
| 스케줄 / 수동 | 실행 이력 | 실행 주체. 수동 실행은 실행한 사람 표시 |
| 재시도 N회 | 케이스 행 | 응답이 없어 다시 보낸 횟수. 펼치면 재시도 뒤 응답을 받았는지 안내 |
| 새로 실패 / 복구 / 계속 실패 / 새 케이스 | 케이스 행 | 같은 스위트·환경의 직전 스위트 전체 실행 대비 변화. 화면 위에 직전 실행 링크 |
| 여기까지 | 결과 화면 | 여기까지 실행. 마지막 케이스 표시 |
| 실패 다시 실행 / 함께 실행 | 결과 화면 / 케이스 행 | 실패만 다시 실행한 실행과 원래 실행 링크, 추출 값 때문에 함께 실행한 앞 케이스 |

- 직전 실행 대비 변화는 스위트 전체 실행끼리만 비교 (단건·여기까지·실패 다시 실행은 비교하지 않음)
- 고친 뒤 확인은 "실패만 다시 실행"

### 11.2 실행 이력

사이드바 "실행 이력"(`/runs`)

- 최신순 20건 단위
- 필터: 프로젝트, 스위트, 환경, 상태, 기간, 실패·오류만
- 행마다 통과·실패·오류 건수. 진행 중인 실행은 진행률

### 11.3 홈 대시보드

사이드바 "홈"(`/`). 기간(최근 7·30일)을 고르면 화면 전체에 적용

| 영역 | 내용 | 표시 조건 |
|------|------|-----------|
| 알림을 보내지 못하는 채널 | 최근 7일 마지막 발송이 실패한 채널, 확인할 점. 누르면 그 채널의 실패 이력 | 있을 때 |
| 점검 중인 환경 | 끝 시각·사유 | 있을 때 |
| 진행 중인 실행 | 진행률·주체 (3초마다 새로고침) | 있을 때 |
| 지금 느린 케이스 | 응답시간 악화 알림 후 회복 전. 누르면 응답시간 추세 | 있을 때 |
| 모니터링 공백 | 스케줄이 제때 실행되지 않은 기간 (10.1) | 있을 때 |
| 요약 | 실행 수, 통과율, 실패·오류가 있는 실행 수와 이전 기간 대비 변화 | 항상 |
| 스위트별 통과율 | 통과율 낮은 순 | 항상 |
| 실패 원인 | 스케줄 실행의 실패·오류를 원인별로 (아래 표). 케이스를 누르면 그 실패 실행 목록 | 항상 |
| 최근 실패·오류 | 5건. "모두 보기"는 실행 이력의 실패·오류만 | 항상 |
| 응답시간이 나빠진 케이스 | 5건. 누르면 스위트 화면의 추세 | 항상 |
| 불안정 케이스 | 실패 구간 2회 이상 또는 재시도한 실행 2회 이상, 최대 10건 | 항상 |

실패 원인 묶음 (알림이 왔을 때 어디부터 볼지)

| 묶음 | 원인 | 먼저 볼 곳 |
|------|------|------------|
| 네트워크 (응답 없음) | 타임아웃, 연결 실패, 연결 끊김, 인증서·TLS 오류 | GW·네트워크·인증서 |
| API (응답은 받음) | 서버 오류(5xx), 요청 거부(4xx), 응답 내용 불일치 | 대상 API, 인증, API 변경 |
| 설정 (요청 못 만듦) | 없는 변수, 잘못된 요청, 막힌 목적지 | 케이스·환경 설정 |
| 기타 | Sentinel 내부 오류 | 관리자 |

- 실패 원인·불안정 케이스는 스케줄 실행만 집계 (수동 실행 제외)

## 12. 배포 때 같은 점검 쓰기 (CI 연동)

배포 파이프라인에서 스위트를 실행하고 결과로 배포 성공·실패를 판단하는 용도. 로그인 세션은 12시간이라 자동화에는 API 토큰 사용

### 12.1 토큰 발급

1. 계정 영역 "API 토큰"(`/settings/access-tokens`) → "API 토큰 발급"
2. 이름(예: `GitHub Actions 배포 확인`), 유효 기간(30·90·180·365일) 선택
3. 발급 직후 한 번만 표시되는 토큰(`snt_…`)을 복사해 CI의 비밀 값에 저장

- 목록에는 앞 8자·만료·마지막 사용 시각만 표시. 필요 없어지면 "폐기"
- 토큰으로 할 수 있는 일은 실행 시작과 결과 조회뿐 (케이스·환경 수정, 변수 조회, 사용자 관리 불가)
- 토큰으로 시작한 실행은 발급한 사람이 실행한 것으로 기록
- 관리자도 다른 사람의 토큰은 보거나 폐기할 수 없음

### 12.2 실행하고 결과 기다리기

저장소의 `scripts/sentinel-run.sh` 사용 (bash·curl·jq 필요). 배포하는 저장소에 복사해 두고 사용

```bash
SENTINEL_URL=https://sentinel.example.com SENTINEL_TOKEN=snt_... \
  scripts/sentinel-run.sh --suite 3 --environment 2 --timeout 600 --junit sentinel.xml
```

| 값 | 찾는 곳 |
|----|---------|
| `--suite` | 스위트 화면 주소 `/suites/3`의 번호 |
| `--environment` | 프로젝트 화면 환경 이름 옆 `#번호` |
| `--junit` | 선택. 결과를 JUnit XML로 저장 (CI 테스트 결과 표용) |

| 종료 코드 | 의미 |
|-----------|------|
| 0 | 모두 통과 |
| 1 | 판정 실패·오류 있음 (실패 케이스 목록 출력) |
| 2 | 실행하지 못함(토큰·권한·없는 스위트), 중지·중단, 시간 초과 |

- `SENTINEL_URL`은 `https://`만 (같은 PC는 `http://localhost` 허용)
- 내부 인증 기관을 쓰는 서버면 `SENTINEL_CA_CERT`에 루트 인증서 경로 (2.5)
- Sentinel이 내부망에 있으면 CI도 내부망 러너(self-hosted)에서 실행
- GitHub Actions 예시는 [api/README.md](../api/README.md) "JUnit XML"

## 13. 변경 이력과 검색

### 13.1 변경 이력

사이드바 "변경 이력"(`/change-logs`). 누가·언제·어떤 설정을 바꿨는지

- 최신순 20건 단위. 필터: 프로젝트, 대상 종류
- 바뀐 항목 이름만 표시, 값은 표시하지 않음 (변수 값·시크릿·비밀번호 보호)
- 바로 열기: 항목 "⋯" → "변경 이력"(그 항목만), 스위트 메뉴(스위트와 소속 케이스·스케줄), 프로젝트 메뉴(프로젝트 전체), 케이스 수정 화면
- 기록 대상: 프로젝트·환경·스위트·케이스·스케줄·점검 시간의 등록·수정·삭제, API 토큰 발급·폐기, 초대 발급·취소, 휴일 등록·삭제, 가입·비밀번호 변경·재설정·사용자 삭제
- 기록하지 않음: 실행 자체(실행 이력에 있음), 같은 값으로 저장한 수정

### 13.2 케이스 검색

- 모든 스위트의 케이스를 이름·경로 일부로 검색 (대소문자 무시, 최대 100건)

## 16. 자주 묻는 문제

### 케이스 1건만 실행했더니 "변수 값 없음" (`UNRESOLVED_VARIABLE`)

앞 케이스가 추출하는 값을 쓰는 케이스. "여기까지 실행"으로 앞 케이스와 함께 실행

### 스위트 실행에서 "변수 값 없음" (`UNRESOLVED_VARIABLE`)

환경 변수·시크릿 이름 오타, 또는 앞 케이스의 값 추출 실패. 앞 케이스 결과의 "값 추출" 표 확인

### dev에서는 통과, staging에서는 "연결 실패" (`CONNECTION_FAILED`)

staging 환경의 기본 URL, Sentinel 서버에서 그 주소로 가는 네트워크(방화벽) 확인

### "인증서·TLS 오류" (`TLS_ERROR`)

대상 서버 인증서의 만료·발급자·이름 확인. 다시 보내도 같아서 재시도하지 않음

### 4xx·5xx인데 "오류"가 아니라 "실패"

응답을 받았으면 상태 코드와 무관하게 판정 규칙으로 판단. "오류"는 응답을 받지 못한 경우

### 실패했는데 알림이 오지 않음

- 수동 실행은 알림 없음 (스케줄 실행만)
- 이미 실패 중인 케이스는 1시간마다만 재알림
- 점검 시간·휴일로 건너뛴 시각은 실행 자체가 없음
- "알림 이력"에서 발송 결과 확인. 보내지 못했으면 확인할 점 안내
- 홈 맨 위의 "알림을 보내지 못하는 채널", 기본 채널 주소 미설정 안내 확인

### 알림 이력 결과가 "로그에만 기록"

기본 채널 주소가 설정되지 않은 서버. 관리자에게 설정 요청 ([deploy.md](deploy.md))

### 밤사이 알림이 하나도 없었음 = 정상?

홈의 "모니터링 공백" 확인. 서버가 멈춰 있었다면 공백으로 기록. 멈춘 즉시 알려면 외부 생존 신호 설정

### 저장할 때 "modified by another request; reload and try again"

그사이 다른 사람이 같은 케이스·환경을 저장함. 새로고침해 최신 내용을 확인한 뒤 다시 수정

### "시크릿 기능이 꺼져 있습니다"

서버에 암호화 키가 없는 상태. 관리자에게 문의

### 스케줄이 예정 시각에 정확히 시작하지 않음

60초마다 확인하므로 최대 1분 정도 늦게 시작할 수 있음. 10분 넘게 늦으면 모니터링 공백

### 결과 화면에 요청·응답 본문이 없음

30일이 지나 원문을 삭제한 실행. 판정·상태 코드·소요 시간은 남아 있음

### 접속할 때 인증서 경고가 뜸

- 내부 인증 기관: 그 PC에 루트 인증서를 등록하지 않음 (2.5). 서버 볼륨을 지워 루트 인증서가 바뀐 경우 새 루트 인증서로 다시 등록
- 보유 인증서: 만료, 중간 인증서 누락, 접속 이름이 인증서에 없음. 관리자가 `scripts/preflight.sh`로 확인

### 초대·재설정 링크가 열리지 않음

만료·사용·취소된 링크. 관리자에게 새 링크 요청
